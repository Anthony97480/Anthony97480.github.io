Projet d'initiation à la recherche

  • Réalisé en 2026.
  • But/Consigne:
    Proposer une solution intelligente, qui esploite les avancées de l'intelligence artificielle, permettant d'accompagner et de facilité les déplacements des personnes TSA (Trouble du Spectre de l'Autisme).
  • Ce qui a été réalisé:
    Dans un groupe de 7 étudiant, il a été décidé, suite aux résultats de l'état de l'art réalisé (ci-joint), de concevoir une application mobile d'aide à la navigation en prenant en compte différents paramètres pouvant engendrer du stresse chez les individus afin de proposer un itinéraire pour un point de départ et une destination donnée.
    1. Description: Projet réalisé en coopération entre l'INSA et le LASS-CNRS de Toulouse. L'application mobile du nom de ASDIA (Autisim Spectrum Desorder Itinary Asistante) est composée d'un front-end, application mobile codée en kotlin et d'un back-end composé de deux serveur, un serveur python FastAPI afin de réceptionner les requêtes et parser correctement les JSONs et de récupérer via des APIs public les informations de la ville de Toulouse concernant les facteurs pouvant engendrer du stresse chez un individus (facteurs décider en amout suite aux recherches effectuées pour l'état de l'art). Ce serveur est en communication avec un autre serveur/code en C++ cette fois-ci, servant uniquement aux calcules des itinéraires à l'aide d'un algorithme dijkstra pondérer par les différents facteurs de stresses et le temps.
      Le principe de l'application est de récolter les données de l'utilisateur via un quiz présent uniquement au lancement de l'application, afin de récupérer les préférences des utilisateurs en fonction de situations données, pour fournir ces informations de stresse au serveur afin de calculer l'itinéraire le plus adapté à l'utilisateur. Et de permettre à l'utilisateur de rentré une demande d'itinéraire et de la ressevoir en l'affichant sur une carte.
      Pour l'instant tous les itinéraires calculés ne fonctionne que sur la ville de Toulouse, étant donnée que toutes les informations sont récupérées via les APIs de cette même ville uniquement.
    2. Technologies: Android studio, FastAPI, Git, Jira et UML/Modèle relationnel.
    3. Langages: C++, Kotlin et Python.
    4. Mon rôle: J'ai été attribué à la réalisation de la partie front-end de l'application en Kotlin et à une partie de la communication du front-end et du back-end via des appels http du coté applicatif afin d'envoyer et de réceptionner les JSONs contenant les information des itinéraires calculées.
  • Rapport du projet: Article scientifique
  • Présentation: Site web de présentation

Projet Système informatique

  • Réalisé en 2026.
  • But/Consigne:
    Réalisé par groupe de deux un compilateur pour une portion réduite du langages C (oppération arithmétique et logique de base, boucle while, condition if else, print) ayant en sortie le langage assembleur/binaire(sur 32bit) correspondant au code C d'entré. Puis réaliser sur un FPGA une architecture RISC avec 5 couche de pipeline et exécuté le code C à l'aide de la sortie binaire produire par le compilateur sur le FPGA.
  • Ce qui a été réalisé:
    1. Description:
      1. Compilateur: Pour le compilateur, il a été décidé de réaliser une implémantion orientée regitre et donc, toutes les variables du code une fois parsé sont enregistrées dans une table des symboles et les indexes de cette table sont utilisés afin de générer la table assembleur (qui est un liste chainé représentant chacune des instructions que devra réaliser notre processeur) qui à la fin de du parsage du code C sera convertie en binaire et retournée dans un fichier. Le contenu de se fichier sera ensuite utilisé Par le processeur RISC.
        Il a également été décidé de tenir trace des éléments dans la table des symboles avec deux variables distincte afin de pouvoir faire la différence entre les variables du code et les variables temporaires nécessaire aux oppérations assembleur. Les deux listes chainées représentant les tables assembleurs et des symboles, sont ainsi réculièrement modifier:
        1. Pour la table assembleur: pour tenir tace des jumps dans le cas des conditions et boucles.
        2. Pour la table de symbole: afin de supprimer les variables temporaires inutiles après parsage mais aussi supprimer les variables en tenant en compte leur profondeurs afin d'empêcher l'utilisateur d'utiliser une variable déclarée dans une structute à l'extérieur de celle-ci.
      2. Processeur RISC: Composé d'un ALU, d'un banc de mémoire, d'un banc d'instruction, d'un banc de registre, et des étages du pipeline afin de relier chacun des différents composants de l'architecture. De nombreuse simplification ont été réalisés dans le code étant donnée le nombre d'instruction et le nombre de bits sur lequels étaient les élément, les signaux vhdl sont le plus souvent sur 4 à 8 bits.
        Par manque de temps, les étages du pipeline, ne prennent en compte que les oppération assembleur COP et AFC.
    2. Technologies: Vivado, Git, FPGA.
    3. Langages: C, Lex, Yacc, VHDL.
  • Rapport du Projet: Rapport
  • Présentation: Site web de présentation

ChatSystem

  • Réalisé en 2025.
  • But/Consigne:
    Par groupe de 2, réaliser une application en Java, permettant la communication entre différents utilisateurs sur un réseau local sans utiliser de serveur.
  • Ce qui a été réalisé:
    1. Description: L'application est capable de détecter sur un réseau local les autres utilisateurs connectés à celle-ci via l'envoie d'une requête UDP en broadcast et celle-ci constitue ainsi une liste des utilisateurs connectés afin de permettre à l'utilisateur de l'application de savoir qui est connecté et de pouvoir communiquer via l'envoie de message TCP au autres utilisateurs présents sur l'application sur le réseau. L'application permet aux utilisateurs de pouvoir de se connecter et se déconnecter de celle-ci (pour être visible ou non sur le réseau) et empêche toutes utilisateurs d'avoir deux même nom d'utilisateur ou d'utiliser un langage ingurier pour se connecter.
      L'application est ainsi à la fois un serveur et un client TCP. L'application met en place une base de donnée SQL en local permettant d'enregistrer les utilisateurs connue (et plus exactement leur ID unique) ainsi que leur conversation afin que même si un utilisateur change de pseudo, l'historique de conversation est concervé. Cependant cette méthode local imposé présente des limites, si un utilisateur utilise un autre ordinateur, celui-ci ne possédant pas la base de donnée local créée par l'application, toutes ces données sont donc inaccessible.
    2. Technologie: Maven, SQLite, Jira, UML/Modèle relationnel et Git
    3. Langages: Java et SQL

  • Présentation: Site Web de présentation
